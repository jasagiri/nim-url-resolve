# ADR-URLR-0001: URI の参照を RFC 3986 §5.2 で解く部品

**ADR ID**: ADR-URLR-0001
**Status**: accepted (2026-11-19 代表が「URL を解く部品の切り出し」と「8 か所すべての置き換え」を承認)
**Date**: 2026-11-19
**Author**: jasagiri (drafted by Claude Opus 5.5)

## Context

相対の URL を基底に対して解く処理は、リダイレクトの `Location`、HTML のリンク、SSE の endpoint、favicon の `href` などで要る。社内のパッケージは、その多くで Nim の std/uri の `combine` を使っていた [測った 2026-11-18: `rg "combine\("` で、7 パッケージの 8 か所]。

`combine` の中の `removeDotSegments` は RFC 3986 §5.2.4 に従っていない [測った: Nim 2.4.2 と devel a6c8c7287]。

| 基底 `http://a/b/c/d;p?q` に対する参照 | RFC 3986 §5.4 | std/uri の `combine` |
|---|---|---|
| `..` | `http://a/b/` | `http://a/b/c/..` |
| `g../h` (RFC の表には無い) | `http://a/b/c/g../h` | `http://a/b/gh` |

上流には、これを直す PR が開いている (nim-lang/Nim #26290、2026-09-27)。直った版が出ても、手元の Nim を上げるまでは届かない。

RFC 3986 どおりに解く関数は、社内の HTML の部品の中に在った。HTML の部品なので、送り先を確かめる部品や HTTP の送り手がそれに依存するのは向きが逆になる。

支配軸: 整合性 (どの部品も、同じ参照を同じ URL に解く)。

## Decision

この部品は、文字列の形を確かめない。解いた結果を URL として読んで確かめるのは呼び手の役目である。HTML が求める前処理 (前後の空白類と、途中のタブ・改行を除く) も持たない。それは HTML の約束で、呼び手 (HTML の部品) の役目である。

- **URLR-01** `resolveReference(base, reference)` は RFC 3986 §5.2.2 の手順で解く。手順は §5.2.2 の厳密な読みで、merge は §5.2.3、dot segment の除去は §5.2.4 に従う。§5.4.1 と §5.4.2 の例は、どれも規格の結果になる。段の途中の `.`・`..` (`g../h`) は段の中身として残す [確かめ方: E。規則 (例で足りる: §5.4 の表が、参照の形の区分 (scheme・authority・空の path・絶対の path・相対の path) を覆う)]
- **URLR-02** 参照が scheme を持たず、基底も scheme を持たないときは失敗を返す (§5.2.1 は、基底に絶対の URI を求める)。基底のフラグメントは、結果に入らない [確かめ方: E]
- **URLR-03** 参照が scheme を持つとき、結果は基底に依らない。参照の path から dot segment を除いたものが結果になる。scheme は小文字にし (§6.2.2.1)、ほかは正規化しない (host の大文字・小文字と、パーセント符号化はそのまま) [確かめ方: E と性質 (どの参照でも、基底を替えて結果が同じ)]
- **URLR-04** `removeDotSegments(path)` は §5.2.4 の手順そのまま。どの入力でも、出力を `/` で切った段に `.` と `..` は無い [確かめ方: E と性質]
- **URLR-05** どの path でも、`removeDotSegments` を 2 度かけた結果は 1 度と同じ。どの参照でも、解いた結果を同じ基底でもう一度解くと、結果は変わらない [確かめ方: 性質]
- **URLR-06** `schemeOf(url)` は、先頭が `ALPHA *( ALPHA / DIGIT / "+" / "-" / "." ) ":"` のとき、`:` の前を小文字で返す。そうでなければ空を返す [確かめ方: E]

公開する手続きは、どれも `{.raises: [], gcsafe.}` である。

## Consequences

- HTML の部品は、HTML の前処理をしてからこの部品に渡す形になる。出力のバイトは変わらない。
- std/uri の `combine` で解いていた 8 か所は、この部品に替わる。RFC 3986 の例で結果が変わるのは、std/uri の不具合に当たる形だけである。

## DQ の宣言

- 仮説の層: 実装。
- 支配軸: 整合性。二次条件: 互換 (std/uri の結果と違う所は、std/uri の不具合の形だけ)。
- 想定する失敗と回避:
  - 4.14 隣を見ない再実装 → 新しく書かず、HTML の部品の実装 (RFC の例を通っていたもの) を移した。
  - 4.1 車輪の再発明 → 標準の std/uri から外れる理由は、測った不具合である。
  - 4.8 早すぎる抽象化 → 使い手は既に 8 か所ある。

## 決めないこと

- 上流の `removeDotSegments` が直った版を手元で使うようになったとき、この部品を std/uri に戻すかどうか。戻せば、どの部品が直った版を使っているかで結果が変わる。
- WHATWG URL の規則 (`\` を `/` に読むなど、ブラウザの読み方)。この部品は RFC 3986 だけを扱う。

## 採らなかった案

| 案 | 判断 |
|---|---|
| 上流の修正 (#26290) を待つ | 開いてから 2 か月近く経っており、直った版が出ても手元の Nim を上げるまで届かない |
| 各パッケージで `combine` の結果を後から直す | 同じ問いに答える仕組みが 8 つになる |
| HTML の部品の関数をほかの部品から使う | 依存の向きが逆になる (送り先を確かめる部品が HTML の部品に依存する) |
| std/uri の `Uri` 型で受け渡す | 型の作りと読み取りの癖 (`parseUri` が例外を上げる) を持ち込む。文字列で受け、文字列で返す |
